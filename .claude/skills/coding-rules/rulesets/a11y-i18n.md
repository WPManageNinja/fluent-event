# a11y-i18n.md — accessibility + internationalization

Triggered when editing any Vue UI change (`src/**`).

## i18n basics

- Every user-facing string runs through a translation helper. Text domain: `fluent-community` (free) / `fluent-community-pro` (pro).
- **PHP**: `__('Text', 'fluent-community')`, `_x('Text', 'context', 'fluent-community')`, `_n('one', 'many', $count, 'fluent-community')`.
- **Vue (portal + admin)**: `$t('Text')` mixin method defined at `src/app.js:233-260` and `src/admin_app.js`. Reads from `window.fluentComAdmin.i18n[string]` (server-supplied translation map). Supports `%s` / `%d` / `%1$s` placeholders. NOT `__()`, NOT `vue-i18n`. Match this pattern.
- **Plurals**: `$_n('1 post', '%d posts', $count)` mixin at `src/app.js:261-268`.
- **Labelize helper**: `$labelize(string)` at `src/app.js:269-282`.
- **Onboarding SPA**: separate context — `src/Onboarding/onboarding.js:17-23` defines `$t` as identity and `$trans` does the actual lookup. When editing onboarding components, use `$trans`.
- **Legacy boot.js**: `src/boot.js:100-102` has its own `$t` shim. Don't reuse — write new code against `app.js` mixin.

## Translation map source

`window.fluentComAdmin` is populated server-side via `wp_localize_script('fluent_community_onboarding', 'fluentComAdmin', […])` (`app/Hooks/Handlers/PortalSettingsHandler.php:192`).

To add a new translatable string used in Vue:
1. Add it inside a `__('...', 'fluent-community')` call in PHP that builds the localized payload.
2. The build / wp-cli `make-pot` extracts it.
3. Reference it via `$t('Text')` in Vue.

Don't hardcode English strings in Vue templates — they bypass translation entirely.

## Escape-after-translate

- `__()` / `_e()` output is NOT sanitized. Translators can return HTML. Wrap with `esc_html__()` / `esc_attr__()` / `esc_html_e()` / `esc_attr_e()` as appropriate. Fix-pattern row: `XSS after translation`.
- Vue's `{{ }}` and `v-text` already HTML-escape — fine for translated strings.
- `v-html` with a translated string = render-time XSS via a malicious translator. NEVER `v-html="$t('...')"` with user-displayed strings.

## Placeholders / parameters

- Use `sprintf` with `%s` / `%d` placeholders. Don't concatenate translated strings (word order varies by language):

```js
// BAD
{{ $t('Hello ') + name }}
// GOOD
{{ $t('Hello %s', name) }}
```

- Comment for translators when context is non-obvious: `/* translators: %s is the user's first name */` in the PHP `__()` call.

## a11y — semantic HTML

- Icon-only buttons need `aria-label` or visible text:

```vue
<button :aria-label="$t('Close dialog')"><i class="el-icon-close" /></button>
```

- Form inputs need associated `<label>` (or `aria-label` for icon-only).
- Status messages use `role="status"` / `role="alert"` so screen readers announce them.

## a11y — focus management

- Modal opens → focus moves to the modal's first focusable element.
- Modal closes → focus returns to the trigger that opened it.
- Don't trap focus in widgets that aren't modal.

Element Plus components mostly handle this — but verify custom modals (`Modules/FullEditorFrame.vue`, custom popovers) implement it.

## a11y — keyboard

- Every interactive element reachable by Tab.
- Enter / Space activates buttons. Escape closes modals / dropdowns.
- Don't override default browser keyboard behavior unless replacing with equivalent.

## a11y — contrast + visible focus

- Visible focus outline on every interactive element. Don't `outline: none` without replacement.
- Color is not the sole indicator (e.g., red text + an icon, not red alone).
- Contrast must hold in BOTH light and dark mode. Use `--fcom-*` CSS variables (NOT hardcoded hex). See `vue.md` → Theming / dark mode section.

## a11y — alt text

- Every `<img>` has `alt`. Decorative images: `alt=""` (empty but present). Informative: describe the meaning.
- Member avatars: `alt` is the member's display name.

## Translation dedup

- One canonical translation per concept. Don't translate the same string in two places — translators handle each independently, and they drift.
- If you find yourself writing the SAME `$t('...')` literal twice across different files, hoist it: a constant, a computed, or a shared component prop.
- Same English string with different `_x()` contexts IS valid (verb vs noun, etc.) — document each with a `/* translators: */` comment.

## Self-audit

For each UI change:
1. Every string runs through `$t()` mixin (no hardcoded English in templates)?
2. Translation wrapped with `esc_html__` / `esc_attr__` when rendered as text/attr in PHP?
3. `sprintf` (`%s`, `%d`) for parameterized strings, not concatenation?
4. Plurals via `$_n` / `_n`?
5. Icon buttons have `aria-label`?
6. Form inputs have labels?
7. Modal focus management correct?
8. Keyboard reachable + visible focus?
9. Images have `alt`?
10. No `v-html="$t('...')"` (XSS via translator)?
11. No duplicate `$t('...')` literals across files — hoisted if reused?

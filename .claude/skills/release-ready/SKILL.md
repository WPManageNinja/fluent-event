# /release-ready — Bump, Translate, Test, Build

Run the release pipeline for FluentEvent. FluentEvent has no pro plugin, so only this repo
changes.

## Input

`$ARGUMENTS`

The first token is the **new version** (for example `1.1.0`). No version → ask the user.

## Steps

Run the steps **in order**. Stop and report when a step fails.

---

### Step 1: Validate and confirm

1. Read the current version from `fluent-event.php` (`FLUENT_EVENT_PLUGIN_VERSION`). The new
   version must be different and must sort higher (`php -r 'var_dump(version_compare("NEW","OLD",">"));'`).
2. `readme.txt` must have a `= NEW (Date: …) =` changelog block. No block → stop and tell the
   user to run `/generate-changelog NEW` first.
3. Check the working tree (`git status --short`). Report any uncommitted change, since the
   build ships the working tree, not a commit.
4. Show the user:
   - Current version → new version
   - The files that change: `fluent-event.php`, `readme.txt`, `language/fluent-event.pot`
   - The zips that the build writes
5. Ask for confirmation before you continue.

---

### Step 2: Bump the version

`fluent-event.php`:
- The header line ` * Version: OLD` → NEW
- `define('FLUENT_EVENT_PLUGIN_VERSION', 'OLD');` → NEW

`readme.txt`:
- `Stable tag: OLD` → NEW

Do **not** change `FLUENT_EVENT_DB_VERSION`. It changes only when a release adds a migration.
If this release adds or changes a table (`database/`), ask the user whether the DB version
needs a bump.

After the edits, grep both files for OLD. Only changelog lines may still contain it.

---

### Step 3: Check the translations

The admin and portal `$t()` / `$_n()` strings translate only when their key is in
`config/i18n.php`. `tests/php/Unit/Lint/AdminTranslationMapLintTest.php` fails when a string is
missing from the map or a map entry is no longer used. Step 4 runs it.

If it fails, add or remove the keys in `config/i18n.php`, then run it again.

The POT is regenerated by the build in Step 5 (`--pot`). The Vue and block strings reach the
POT through their PHP maps (`config/i18n.php`, `PortalHandler::strings()`,
`BlockEditorHandler::strings()`).

---

### Step 4: Run the tests

```bash
npm run test:all
```

This runs the Vitest suite and the PHPUnit suite. Stop on any failure, and show the output.

---

### Step 5: Build and package

```bash
bash build.sh --node-build --pot
bash build.sh --wporg
```

- The first run builds the assets (`npm run build`), regenerates `language/fluent-event.pot`,
  and writes `builds/fluent-event-NEW.zip`, the zip for direct installs (it keeps the
  self-hosted updater).
- The second run reuses the assets and writes `builds/fluent-event-NEW-wporg.zip`, the
  WordPress.org zip (no updater).
- `build.sh` reads the version from `fluent-event.php`, so the zip names follow Step 2.
- `npm run build` sets `config/app.php` to production; `build.sh` restores the file. Check
  `git diff config/app.php` after the build. It must show no `env` change.

Then verify each zip:

```bash
for z in builds/fluent-event-NEW.zip builds/fluent-event-NEW-wporg.zip; do
  unzip -p "$z" fluent-event/fluent-event.php | grep -E "Version:|FLUENT_EVENT_PLUGIN_VERSION'"
  unzip -p "$z" fluent-event/readme.txt | grep "Stable tag"
  unzip -p "$z" fluent-event/config/app.php | grep "'env'"
done
unzip -l builds/fluent-event-NEW-wporg.zip | grep -c PluginManager   # must be 0
```

---

### Step 6: Summary

- **Version:** OLD → NEW
- **Files changed:** `fluent-event.php`, `readme.txt`, `language/fluent-event.pot`
- **Translations:** the map lint result, and the POT string count change
  (`grep -c '^msgid ' language/fluent-event.pot` before and after)
- **Tests:** pass/fail counts
- **Zips:** both paths, their sizes and `shasum -a 256`
- **Next:**
  - Commit the release through `/commit-push-pr` when the user asks. This skill never commits,
    tags or pushes.
  - Run `/plugin-check` before a WordPress.org upload.
  - Run `/generate-release-note NEW` for the blog post.
